# 화면 디자인 만들기와 스스로 검수하기

사용자는 대개 “재고 앱 만들어줘”처럼 기능만 말한다. 디자인을 따로 부탁받지 않아도 화면이 있는 작업이면 이 순서를 따른다. 승인 절차를 늘리는 지침이 아니다. 정해진 것은 다시 묻지 않고, 정하지 않은 것은 스스로 정해 짧게 알린 뒤 진행한다.

## 적용 범위

| 작업 | 적용 |
| --- | --- |
| 새 화면, 화면 구성·색·글꼴·여백을 바꾸는 작업 | 1~6 전체 |
| 기존 디자인 유지, 지정한 부분만 수정 | 1과 5·6. 새 스타일을 만들지 않는다 |
| 화면이 없는 작업(계산·저장·서버) | 적용하지 않는다 |

기능과 변경 범위는 최신 사용자 요청·저장한 프로젝트 지시·완료조건이 정한다. 이 지침은 기능을 추가하거나 디자인 변경 범위를 넓히는 근거가 아니다.

## 1. 정해진 것부터 확인한다

- 사용자가 말한 느낌·색·참고·스타일 번호, 저장한 프로젝트 지시, 확정 토큰과 선택 프로필, 프로젝트 기억, 앱의 `DESIGN.md`를 먼저 읽는다. 스타일 키나 참고, “알아서” 위임이 적혀 있으면 그대로 따르고 같은 것을 다시 묻지 않는다.
- 참고 이미지나 화면이 있으면 참고 디자인 분석 지침으로 실제 원본을 본다. 그 결과가 아래 계획의 출발점이다.
- 아무것도 정해지지 않은 새 화면이면 만들기 전에 멈추고 한 번만 묻는다. “원하는 디자인이나 참고할 사이트·이미지가 있으면 알려 주세요. 아래 스타일 중 번호로 골라도 됩니다(전체는 `ui/style-preview.html`을 열면 타일로 볼 수 있습니다). 없으면 제가 정해서 진행하겠습니다.” 번호 목록은 `docs/STYLES.md`에서 앱 종류에 맞는 6~8개를 번호·이름·한 줄 설명으로 붙인다. 답을 기다린 뒤 진행한다. 요청이 분명해도 건너뛰지 않으며, 다른 꼭 필요한 질문이 있으면 같은 메시지에 함께 묻는다.
- 참고를 받으면 그것이 출발점이다. 사이트 주소는 직접 열어 볼 수 있을 때만 보고, 볼 수 없으면 화면 캡처를 부탁한다. 보지 않은 것을 본 것처럼 따라 하지 않는다. 번호를 고르면 `docs/STYLES.md`의 그 키로 `ui/design-presets.js`의 색·여백·모서리·글꼴을 출발점으로 삼는다. 없다고 하거나 맡긴다고 하면 2번으로 가서 스스로 정한다.
- 답은 디자인 기록에 남기고(스타일은 번호가 아니라 키로) 같은 프로젝트에서 다시 묻지 않는다. 기존 디자인을 유지하는 작업과 작은 수정에는 묻지 않는다.

## 2. 코드보다 계획을 먼저 쓴다

다섯 가지를 짧게 적는다.

1. **무엇을 위한 화면인가**: 주제, 쓰는 사람, 이 화면에서 가장 중요한 한 가지 일.
2. **색**: 역할 이름과 값 4~6개. 배경, 표면, 본문, 보조 글자, 강조, 상태.
3. **글꼴**: 제목용과 본문용. 필요하면 숫자·표용. 크기 단계와 굵기.
4. **배치**: 한 문장 설명과 글자로 그린 간단한 스케치. 넓은 화면과 좁은 화면을 각각.
5. **기억될 한 가지**: 이 주제에서 나온 특징 하나. 대담한 선택은 여기에만 쓴다.

쓴 뒤 스스로 묻는다. “이 계획을 전혀 다른 앱에 붙여도 그대로 통하는가?” 그렇다면 주제에서 나온 선택이 아니라 습관이다. 해당 항목을 그 주제의 재료·도구·말투에서 다시 고른다. 크림색 배경에 세리프 제목, 검은 배경에 형광 강조색, 큰 숫자 카드 세 장처럼 어디에나 나오는 구성은 주제가 요구할 때만 쓴다. 사용자가 그 모양을 원했다면 그대로 따른다.

계획은 앱 폴더의 `DESIGN.md`에 남기고([기록 양식](references/design-record.md)) 사용자에게 두세 줄로 알린 뒤 바로 진행한다. 다음 대화의 에이전트가 이 파일을 읽고 같은 디자인을 이어간다.

## 3. 구도를 먼저 맞춘다

- 실제 내용과 실제 데이터 모양으로 뼈대를 만든다. 색과 장식은 아직 넣지 않는다.
- 넓은 화면과 좁은 화면을 실제로 열어 본다. 첫 화면에서 가장 중요한 내용과 주요 행동이 보여야 한다. 안내문·필터·설정이 결과보다 먼저 화면을 차지하면 구도가 틀린 것이다.
- 구도가 틀렸으면 색·글꼴을 손대기 전에 구도부터 고친다. 틀린 배치를 꾸며서 가리지 않는다.

## 4. 계획대로 입힌다

- 색·글꼴·간격은 계획의 값만 쓴다. 한 곳(CSS 변수나 프로젝트의 토큰 파일)에 정의하고 화면에서는 그 이름을 쓴다.
- 구분선·번호·작은 머리글 같은 장치는 내용의 실제 구조를 나타낼 때만 쓴다. 순서가 없는 항목에 01·02·03을 붙이지 않는다.
- 움직임은 필요한 한 곳에만 쓰고 `prefers-reduced-motion` 설정을 지킨다.
- 버튼·입력의 기본·포커스·비활성·오류 상태와 빈 화면을 만든다.
- 글꼴은 [글꼴 고르기](references/typography.md), 문구는 [화면 문구](references/copy.md), 한글 줄바꿈과 숫자는 [한국어 화면](references/korean-text.md)을 따른다.

## 5. 보내기 전에 스스로 검수한다

코드나 검사 통과가 아니라 **실제로 그려진 화면**을 본다. 자세한 항목은 [검수표](references/review.md)에 있다.

1. 넓은 화면과 좁은 화면, 가능하면 320 CSS px에서 연다. 그 사이에서 단 수나 배치가 바뀌는 화면이면 중간 폭(768px 안팎)도 연다. 빈 상태와 긴 한글·큰 숫자가 든 상태를 함께 본다.
2. 2초만 보고 묻는다. 무슨 화면인지, 어디를 누르면 되는지 알 수 있는가.
3. 가장 약한 세 곳을 찾아 고친다.
4. 잘림·겹침·오탈자·어긋난 정렬·읽기 어려운 대비·문장 끝 한두 글자만 남은 줄은 사용자가 찾기 전에 고친다.
5. 고친 화면을 다시 연다. 고치기 전에 본 화면으로 통과를 말하지 않는다.

화면을 열 도구가 없으면 시각 검수 미실행이라고 보고한다. 기능 검사 통과와 화면 검수 결과는 별개이며 따로 보고한다.

## 6. 남긴다

- 실제 결과에 맞게 `DESIGN.md`를 고친다. 계획과 달라진 부분과 이유를 적는다.
- 작업을 마칠 때 화면 검수를 실제 결과대로 검사 항목에 넣는다. 예: “화면 검수(넓은·좁은 화면): 통과”, “320px 확인: 미실행”.

## VAS 프로젝트에서 추가로 확인할 사항

- 새 앱의 기록 위치는 `src/DESIGN.md`다. 기존 앱은 그 앱의 디자인 문서나 토큰 파일을 따르고, 없을 때만 앱 원본 폴더에 만든다.
- 참고 이미지 분석은 `.agents/skills/design-analysis/SKILL.md`, 선택 프로필은 `.agents/skills/designer/references/profiles/<프로필키>.md`를 읽는다.
- VAS 프로젝트에는 제목용 영문 글꼴 6종이 라이선스와 함께 들어 있다(스타일별 글꼴 파일은 `docs/STYLES.md`). 쓰려면 그 파일과 같은 이름의 `-OFL.txt`를 함께 앱 자산(`src/assets/fonts/`)으로 복사하고 `@font-face`로 선언한다. 한글은 PC 글꼴로 보인다. 그 밖의 글꼴은 사용자가 준 파일이나 라이선스를 확인한 것만 쓰고, 없으면 시스템 글꼴 스택을 쓴다. 견본 그림은 들어 있지 않다. 앱이 `ui/` 경로에 의존하게 만들지 않는다.
- 참고를 물었던 답은 `python -B scripts/vas.py plan --decision "디자인: 스타일 키, 참고 또는 알아서 위임 (사용자)"`로 프로젝트 기억에도 남긴다.
- 작업을 마칠 때 화면 검수 결과를 `done`의 `--check`에 실제대로 전달한다. 화면 세션 절차로 작업했으면 `finish`의 `--check`와 관련 완료조건의 관찰에도 적는다.
