# VAS 2.11.0 — Your project folder, shared instructions and verified visual references

VAS 2.11.0 makes the extracted Windows release folder the application project. The user's code belongs in root `src/`; VAS's supporting tools live in `.vas/`. A saved project prompt connects the settings screen to the coding agent's next task, while reference analysis and rendered checks help the agent apply a chosen visual direction within the requested feature scope.

The focus remains the complete work cycle: understand the request, read the current project, carry context into implementation, collect real checks, address remaining issues and resume later. Design is supporting context in that cycle. VAS supplies instructions and comparison tools; the coding host supplies the actual implementation, image inspection, browser, command and delegation capabilities.

## Start with the project itself

Download **`VAS-2.11.0-windows.zip`** from the release assets, extract the entire archive into a new folder, rename that folder for the app and open it in your coding AI. Rename it before creating its first saved session.

```text
your-project/
├── src/                       Your application source
├── .vas/                      VAS runtime, screens, CLI and guides
├── .agents/                   Project instructions and bundled skill
├── AGENTS.md                  Host entry instructions
├── Run-VAS-System.bat          Start VAS settings
└── VAS-PROJECT-PROMPT.json     Created by saving project instructions
```

The generated project instructions distinguish application work from VAS maintenance. They direct the agent to read the application's own rules and source, keep VAS tooling separate and use the user's requested stack. Opening the folder does not grant additional permissions or start an agent in the background. VAS settings and the application are separate screens; the coding host starts the app using its own run procedure.

**Choose the named Windows asset, not GitHub's Code → Download ZIP or automatic “Source code” archive.** Those downloads contain the VAS development repository, where root `src/` is VAS product source. The standalone client form and GitHub Pages are also separate from an application starter.

See the [project-folder guide](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.11.0/docs/PROJECT-ROOT.md).

## One saved brief for the screen and agent

The starter hub now edits project working instructions in the root `VAS-PROJECT-PROMPT.json`. For example, save “Build an inventory app; preserve quantities after reload; do not add accounts or payments,” then tell the coding chat to proceed using those instructions.

Before the first request, resume, implementation and delegation, the project instructions direct the host to read the current file through the bundled CLI:

```powershell
python -B .vas/scripts/vas-project-prompt.py get
```

The host normally runs this command; the user does not need to maintain CLI records manually. The portable prompt can be read before a private task session exists. When a task is prepared, the prompt revision and content are linked to its context so an old preparation cannot silently stand in for changed instructions.

Saves are revision checked. An outdated editor cannot silently overwrite another tab's newer instructions, and save or corruption errors remain visible. The current explicit user request and higher-priority host rules still apply. Stored instructions do not authorize unrelated actions or establish that work was tested.

Saving does **not** wake an idle AI, interrupt an active run or automatically replace a conversation's memory. An old prompt already pasted into another tool also does not update itself. The host must reread the file and prepare current instructions before continuing. Portable project instructions and PC-private sessions are distinct: successful prompt access does not imply successful session storage or restoration.

## Apply visual elements within the actual task

Design samples now carry an explicit visual-only reference policy through browser handoffs and chat preparation. The five reference elements are **typography, color, layout, imagery and spacing**. App features come from the actual request, saved project instructions, constraints and completion conditions.

Selecting a subscription sample for an inventory app can influence row alignment, heading proportions, spacing and accent colors. It does not ask the agent to add pricing plans, checkout or billing. Similarly, a music sample does not make a playlist part of a calendar app. Explicitly requested commerce or account features remain valid requirements; this is scope separation, not a keyword ban.

Built-in preset and profile instructions describe visual relationships to adapt. Sample branding, text, records and page counts are not application requirements. Existing-design preservation and limited-change scopes remain in effect; the reference does not grant permission to redesign unrelated screens or override confirmed tokens.

See [design reference scope](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.11.0/docs/DESIGN-REFERENCE-SCOPE.md).

## A bundled skill for your own reference images

The **design-analysis** skill is included in the project instructions, compatible host skill locations and active design handoffs. No global skill installation, Obsidian connection or additional API key is needed to use its workflow.

The agent is instructed to:

1. Inspect the actual reference and identify the source and visible region.
2. Analyze typography, color, layout, imagery and spacing, including how they relate.
3. Separate observed facts from proposed font choices, sizes, colors or responsive behavior.
4. Map those choices to the requested app's screens and components.
5. Implement within the authorized scope and check the actual rendered result.

An analysis-only request stops after analysis. An implementation request continues through authorized implementation and checking without adding a separate approval ceremony. Missing images, unviewed sources and unknown mobile or interaction states remain explicit. A filename, URL, attachment count or another agent's summary does not prove direct image inspection.

Attach the actual reference image to the coding chat. The VAS form's file picker passes attachment counts, not image contents. VAS itself does not recognize image pixels or upload them to an AI service; the host must provide image inspection and implementation tools. Supporting agents receive the same analysis, requirements and accessible reference, with unavailable sources identified.

See [reference analysis and checking](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.11.0/docs/DESIGN-ANALYSIS.md).

## Check the application that was rendered

The guidance now makes several common visual failures explicit:

- Check PC and mobile widths, including 320 CSS px and nearby layout breakpoints. Inspect clipping, overlap and reachable controls, not only page overflow.
- Exercise empty, normal, long Korean text and large-number states, then test primary actions, keyboard focus and persistence after reload.
- Verify the actual font used for Latin text and numbers separately from Korean fallback. A CSS font declaration is not a loading result.
- Use bundled fonts as app-owned assets when appropriate, including their OFL licenses. The app should not depend on a VAS runtime URL or an arbitrary remote font service.
- Measure small captions and placeholder text against their actual backgrounds. Follow WCAG 2.2 text-contrast and reflow criteria; distinguish decorative accent colors from readable text variants without silently changing fixed user tokens.
- Separate host-performed checks, independent checks, unavailable tests and remaining differences.

These are instructions for verification, not an automatic repair service. Fixes found in isolated example apps do not change all user applications or establish universal visual accuracy.

## Upgrade safely

The Windows package layout changes from 2.10.x. Use a fresh installation rather than overwriting an active project.

1. Close the old runtime and back up the existing installation, actual app and user files.
2. Extract `VAS-2.11.0-windows.zip` into a new folder and give it the final project name.
3. Preserve your application source, assets, configuration and any `VAS-PROJECT-PROMPT.json`. Transfer application-owned files deliberately, checking conflicts with starter instructions. An older VAS tool `src/` is not the user's app source.
4. Open a fresh coding conversation in the new folder. Have the agent read the current prompt and actual files, identify the intended target and establish the current task context.
5. Check the app and saved instructions before removing or reorganizing the older installation.

There is **no automatic migration** of PC-private sessions, progress or target bindings to a new path or PC. Copying the project prompt or a public settings export does not recreate those records. Existing app instructions must be reconciled, not blindly replaced. Retaining the old installation keeps its original context available for reference while the new project is checked.

Older supported settings remain compatible; missing historical records remain absent. The handoff v3 and result v1 contracts, opt-in memory, bounded storage, privacy review and conservative assessment boundaries remain in place. The project prompt is not an app backup or an execution receipt.

Requirements remain Windows 10 or 11, PowerShell 5.1 or later, and Python 3.10+ available to the coding host for CLI operations. VAS does not bundle Python or a coding AI. `VAS-Client-Form-2.11.0.zip` remains a separate standalone form. `SHA256SUMS.txt` and `release-manifest.json` identify the release artifacts and packaged source.

## Verification and known limits

The [2.11.0 verification record](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.11.0/docs/verification/2.11.0-project-workflow.md) separates product regressions, extracted-package checks and application observations. Published CI results are available in [GitHub Actions](https://github.com/zmsqnfl-commits/quintpact-vas/actions).

Independent Windows Chrome checks inspected Bento, Swiss and external-image example applications at 1440, 390 and 320 CSS px, plus targeted breakpoints and data states. They found and corrected example font loading, text contrast and long-data layout issues. The reference elements were applied to the requested inventory behavior without adding unrelated sample functions.

Two fresh Bento/Swiss coding-host runs reached their 480-second deadlines after producing application files and attempting restricted browser or private-session access. They are **not completed autonomous end-to-end runs**. Their later independent rendering checks are separate evidence. The external-image example originated in the preceding image-analysis check; it was subsequently inspected and corrected independently. The final strengthened guidance was regression tested, but those fresh host generations were not rerun against every final wording change.

The visual observations use Windows Chrome with resized viewports and local HTTP. They do not claim physical Android or iOS testing, Safari coverage, `file://` app execution or full accessibility conformance. The three examples are bounded observations, not a reliability rate for every model, host, reference image or project.

Implementation reports, VAS assessment and user acceptance remain separate. Automatic-only work does not acquire an invented manual approval step; genuine failures and original outstanding conditions still need action. Private paths, conversations, runtime credentials and raw host logs remain outside the public product and release assets.
