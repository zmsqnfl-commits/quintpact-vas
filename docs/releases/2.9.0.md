# VAS 2.9.0 — Start in chat, keep design and execution connected

VAS 2.9.0 adds a conversational workflow to the existing visual setup and prompt-copy tools. Open the VAS folder in a coding host that reads its project instructions, describe a new app or an existing change, and continue with saved task settings. The local Design Studio can edit that same task's design. The coding host then reads the latest settings, works on the actual application and reports evidence against the original completion conditions.

The release keeps the handoff v3 and result v1 contracts. It does not add an application backend, a cloud task service or an autonomous agent runtime. Implementation, browser access, subagent calls and test execution use the coding host's actual tools and permissions.

## Conversational startup

The shared startup instructions distinguish three requests: creating a new application, modifying an existing application, and developing VAS itself. The actual application folder is kept separate from VAS. Existing application rules and source files are read before implementation; VAS's own technology choices are not imposed on another project.

The agent asks for missing information that affects the result, continues clear requests without repeating onboarding, and respects a request for planning only. Hosts that cannot read the additional instruction files can still use the startup procedure embedded in the root entry files. This depends on the host actually loading those files; selecting a folder does not launch an AI in the background.

## Persistent local task settings

The Python CLI stores a sanitized task summary: requirements, constraints, design scope, completion conditions, questions and the next step. A private binding retains the target folder and directory identity outside the product tree. Shared settings and exported handoffs do not contain that private target path.

Fresh conversations can resume tasks on the same PC and VAS installation. Multiple tasks require a selection. Missing, replaced or unsafe targets are reported for review rather than matched to a similarly named folder. Saves use expected revisions and protected local-store operations; a stale writer cannot overwrite a newer revision. Forgetting a session removes its settings and binding, not the application's files.

Saved settings are reference data. They do not preserve execution permission, test evidence or an authoritative completion state. Work-memory and RAG consent remain separate.

## Connected Design Studio

The local studio connects to an explicitly selected session. Users can compare presets and samples, adjust the design direction and tokens, and commit the choice with **Save to chat settings**. The browser only changes design fields and the permitted design scope; it does not rewrite the request, completion conditions or target binding.

The screen checks for updates about every four seconds while visible and when refocused. Clean screens adopt incoming changes. An edited screen keeps its draft and reports a revision conflict, with an explicit action to discard the draft and load the latest settings. It does not silently merge or force-save conflicting changes.

Session themes and undo history are isolated from other sessions and the standalone theme. Sample pages are read-only comparisons and retain the session link when returning to the studio. They do not commit a design merely because the user explored another style.

Existing projects preserve their design by default. Partial changes require a named scope; a redesign requires an explicit selection. Preserve mode does not turn saved presets into active styling instructions. Browser responses expose target status without exposing the private path or directory identity.

Saving in the browser does not wake the coding AI. The main agent rereads the latest session before the next request, implementation, delegation or settings write.

## Current handoffs for implementation

`prepare` produces a handoff bound to the session ID, revision, settings hash and role-resource hash. The outer response is `prepared` only when a task request and at least one required completion condition are present. Otherwise it returns `needs-input` with the missing fields. The handoff's internal READY state continues to mean that handoff material exists, not that implementation or verification succeeded.

Active designs carry the confirmed direction, full token values, profile rules and visual-reference information. Preserve mode excludes active styling instructions. Unknown profiles remain identified as unverified instead of being replaced with another style. An oversized execution prompt is rejected rather than silently truncating its instructions.

The main coding agent reads the target application's rules, source and actual verification commands. Where the host provides subagent tools and independent work is useful, it passes full role instructions, assigned files, constraints, design rules and completion conditions, then collects the results. Without those tools it performs the work sequentially. Role-definition files alone do not establish that an agent was invoked or given an isolated sandbox.

The main agent checks current settings again at implementation, delegation and result-collection boundaries. If settings change, it compares the new scope with the work already performed and repeats affected checks. An old report cannot become current merely by replacing its handoff ID.

## Conservative result assessment

`assess` accepts a result v1 document and compares its handoff ID, payload hash, source type and iteration with the current prepared handoff. Stale revisions, changed role resources and mismatched reports are rejected. Results retain the original completion-condition IDs and identify the actual artifact version inspected.

| Information | Meaning |
| --- | --- |
| Actual host execution | Tool calls, commands, exit codes and observed artifacts establish what ran. |
| `reportedStatus` | The coding agent's submitted status. It is not independent confirmation. |
| `assessment` | VAS's comparison with the original conditions and submitted evidence. Failures, blockers or scope violations remain incomplete. |
| User confirmation or acceptance | A separate fact about the actual result; imported JSON flags cannot create it. |

This CLI does not collect direct user observations. Agent-submitted passing tests can therefore have an assessment of `needs-verification`. That status does not erase the tests that actually passed; it keeps the remaining confirmation visible. Neither `prepare` nor `assess` runs application code, executes tests, certifies another AI's work or adds a new approval requirement to already authorized implementation and ordinary checks.

## Local runtime and distribution

The Windows runtime exposes authenticated routes to list public session summaries, read a selected session and save its design with a revision check. Those routes do not create or rebind application targets and do not execute application code. Session-store files and private bindings are excluded from source imports, product archives, backups and the public site.

The request loop also handles a failed response after headers have been sent without terminating the server. Normal handler failures still return the existing HTTP 500 error response; authentication and origin checks are unchanged.

The Windows package includes the session CLI, connected design screen, shared role resources and user guides. The standalone form and GitHub Pages remain useful for visual comparison and prompt preparation but cannot access the PC's chat-session store. Bundled runtime assets continue to use local fonts and media without external CDNs.

## Support and verification boundaries

The complete local workflow requires Windows 10 or 11, PowerShell 5.1 or later, Python 3.10+ available to the coding host, and access to the private settings store. Python and a coding AI are not bundled. A restricted Windows host may open the VAS project yet be unable to read its private store; VAS reports that failure without weakening permissions or silently relocating the store.

Product verification and application verification are separate. Product gates cover session contracts, privacy boundaries, revision conflicts, browser synchronization, Windows HTTP handling and extracted-package behavior. Actual-host checks separately exercise instruction discovery, fresh-conversation resume, current handoff preparation and result linkage.

An actual implementation/reviewer delegation exercise demonstrated role invocation and result collection. That evidence does not imply that every application run delegates work: a separate fresh-install application exercise used sequential execution. Browser tests and artifact inspection establish only the checks actually performed; they do not certify native Excel behavior or every direct-file opening environment. A host repair timeout is an interrupted execution, not a completed run, and its artifacts require separate inspection before reporting their status. Unperformed manual checks remain visible as `needs-verification`.

Release workflow results provide the final artifact-specific gate status. Earlier application exercises do not substitute for release gates or user acceptance. Internal task boards, raw host transcripts and private execution records are not included in the product distribution.

## Upgrade and compatibility

Download `VAS-2.9.0-windows.zip`, verify the published checksum and extract the entire archive. Keep a backup of the previous installation and user data. Open the extracted VAS folder in a fresh coding-host conversation, or launch `Run-VAS-System.bat` for the established screen-based flow. `VAS-Client-Form-2.9.0.zip` remains the standalone request form.

Session storage is associated with the VAS installation path. Extracting to a new path or switching PCs does not migrate the previous installation's tasks automatically. Shared setting exports omit private bindings and do not restore those bindings by themselves. See [saved settings](../CHAT-STATE.md) before moving an installation with active tasks.

Existing handoff v3/result v1 documents and standalone design selections remain compatible. The earlier [scope and completion policy](../completion-policy.md), [2.8.1 recovery behavior](2.8.1.md) and [2.8.2 distribution boundaries](2.8.2.md) remain in effect. The screen-based brief, optional JSON export, sample websites and Morrow continue to be available.
