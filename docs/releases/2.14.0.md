# VAS 2.14.0 — The project remembers its own work

## Project memory in the project folder

A project now keeps what it knows in `vas-state/` inside the project folder, as Markdown that a person or any coding host can read and edit.

- `vas-state/now.md` is the current state on one page: the request, the target, completion criteria, decisions with their reasons, open questions, the next step and the last check.
- `vas-state/log/` holds one numbered record per finished piece of work: what was done, why, how it was checked, what was tried and did not work, and the next step.
- `vas-state/index.md` lists the records one per line and is rebuilt from them.

`python -B scripts/vas.py start` shows the current state and the most recent records. `plan` writes the agreed scope, `done` adds a record and updates the page in one write, and `recall "words"` returns the records that bear on a request so the agent opens only those. Reading stays bounded as records accumulate.

Because the memory is in the folder, it follows a renamed, moved or copied project and is the same for every host. Nothing is written outside the project. Credentials and absolute paths are redacted before saving, changed files are stored as relative paths, and records are only ever added. Two hosts that finish at the same moment receive different record numbers.

A host without Python follows `.agents/MEMORY.md` and edits the same files directly. Hand-written files, unknown sections and damaged records are read as far as possible and are not overwritten.

The entry instructions now use this flow by default. Sessions created from the screen-based workflow keep the existing private store and the `prepare` and `finish` procedure. Shared progress notes written by earlier versions under `vas-state/progress/` are still shown by `start` for reference.

## Design craft

The bundled design-craft skill applies to any task with a screen, even when the request does not mention design: a short plan before coding, composition settled with real content, and an inspection of the rendered result before delivery. Decisions are kept in the app’s `DESIGN.md`. It reaches every host through the entry instructions, the handoff workflow, the role definitions and the Claude skill folder.

## Smaller changes

- Common error responses carry a `hint` that says what happened and what to do next. Conflict hints never include a revision number: read the current state again before retrying.
- `start` no longer describes a missing private session as another host; it names the likely causes, including a renamed folder.
- `start` warns when the shared progress journal is close to its slot limit.
- `finish` without arguments still only reports status, and now says that nothing was recorded.
- The release build moves ZIPs that belong to another version to `dist-previous/` instead of deleting them with the output folder.
- Three PowerShell tests no longer depend on the console code page.
- Path-boundary checks and the canonical digest are each defined once.

## Verification

Linux: 1,599 Python tests passed with 144 skipped for Windows PowerShell, 194 browser tests passed with 6 skipped, and the package and release-boundary checks passed. Windows: the changed areas, the integrity check and the runtime checks passed on a Korean-locale PC, including three consecutive runs of the concurrent-write test.

A real host followed the new entry instructions: a fresh Claude Code cloud session cloned the repository, read `CLAUDE.md` and built a one-screen inventory app from a single request without asking a question. Its environment blocked `scripts/vas.py`, so it used the documented fallback and wrote `vas-state/now.md`, `index.md` and `log/0001.md` by hand in the `.agents/MEMORY.md` format. It wrote a design plan to `src/DESIGN.md`, inspected the screen at 1280, 390 and 320 px, fixed three issues it found, and reported what it had not checked.

Not verified in this release: a real host using the `plan`, `done` and `recall` commands (the host above could not run them), a second conversation continuing from the saved memory on a real host, Codex, concurrent writes on a network share, and the complete Windows suite after the final change. One PowerShell module test fails when the repository itself is on a network share, because the execution policy blocks unsigned modules from a remote path; it passes from a local disk.
