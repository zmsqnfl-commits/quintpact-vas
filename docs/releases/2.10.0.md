# VAS 2.10.0 — Connected agent work, resumable progress and actionable verification

VAS 2.10.0 helps the main coding agent carry a task from the initial request through implementation, verification and the next conversation. It adds explicit blocking questions, a latest progress checkpoint, scoped execution records with selected file observations, and follow-up actions derived from the assessment.

The user can open the VAS folder in a supported coding host and describe the work in ordinary language. The host handles the settings and execution records; users do not need to write JSON or manually operate each session command. The optional Design Studio and existing screen-based handoff remain available.

This release builds on [2.9.2](https://github.com/zmsqnfl-commits/quintpact-vas/releases/tag/v2.9.2). It preserves handoff v3, result v1, the existing consent and storage policies, and the separation between host execution, VAS assessment and user acceptance.

## Resolve blocking decisions without turning every question into a stop

Saved settings now distinguish ordinary `questions` from optional `blockingQuestions`. A reference question remains available to the agent; a blocking question describes a decision required before preparing implementation instructions. Both lists and the actual `nextStep` are included as reference context in the prepared handoff.

If blocking questions remain, `prepare` returns `needs-input`. The main agent resolves them, records the decisions in the full settings and removes the answered questions before preparing again. Existing settings without `blockingQuestions` keep their previous behavior; ordinary questions are not silently converted into blockers.

Missing task requirements, missing required completion conditions and privacy-review requirements still prevent a ready handoff. Stored questions and next steps are reference data, not additional execution permissions.

## Resume the work, not just the original settings

A progress checkpoint retains one latest summary containing the current phase, decisions and reasons, changed relative files, performed and unperformed checks, unresolved items and the next action. A new conversation reads that summary alongside the current settings, then inspects the actual project before continuing.

The host saves the summary with `checkpoint`, which atomically updates the progress record and the settings' `nextStep`. Session and progress revisions are checked independently, and both advance on a successful checkpoint. The host reads the result back to confirm it was saved. A conflict or failed write preserves the earlier record and must be reported as unsaved work.

An available summary is useful context, not proof that the current files pass. A stale summary identifies its context mismatch; an invalid summary is not silently erased or replaced. A checkpoint itself does not run tests, restore a whole conversation or back up application files. It can make an older execution context stale even when application files are unchanged.

The latest progress record is limited to 16 KiB and remains inside the existing private session-store limit of 2 MiB and 64 sessions. It excludes raw chat, source code, raw logs, private absolute paths and credentials. Progress does not automatically enter public exports, browser responses or prepared handoffs; the main agent selects the context needed for supporting work.

See [progress and resume](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.10.0/docs/CHAT-PROGRESS.md).

## Connect actual role returns to scope and selected files

The main agent can open one latest execution record linked to the prepared session, settings, role resources, target and original completion conditions. Before each implementation, review or verification unit, `work start` records its role, direct or delegated mode, allowed write scope and selected files to observe. After actual host work returns, `work finish` records the observed call identifier, return state, changed files and condition results.

Implementation and verification are separate work units. A verification unit observes its selected inputs immediately before the actual check, then records the return afterward. `work inspect` compares selected-file size, presence and SHA-256 observations with the current files. This avoids treating a fingerprint from before implementation as proof of what a later test checked.

- Failed reviews remain failures even when another verification passes.
- Pending, timed-out, cancelled and unreturned work remain visible. The main agent must confirm the real host's return or termination before retrying; VAS does not stop that host process.
- Reported or observed out-of-scope changes remain visible. A successful replacement check does not erase a historical scope violation.
- A relevant file change identifies the affected unit and conditions. Unrelated stable samples can remain candidates for reuse.
- Reordered conditions, changed settings and changed role resources are compared through the original context. Old identifiers are not relabeled as new evidence.

Execution records have independent revisions, so a stale writer cannot overwrite a newer return. One latest record permits up to 12 work units, 20 conditions and 64 selected files, within a 128 KiB record limit. Selected-file reads are limited to 1 MiB per file and 16 MiB per observation. Exceeding a bound preserves the existing state and requires the host to narrow or divide the work.

These are scoped observations. VAS does not execute the recorded command, authenticate a submitted host call ID or certify the report. Fingerprints cover only the selected files at the observed times; omitted inputs, external tools and changes elsewhere are outside that sample. Actual commands, results and delegation must be checked in the coding host.

See [work records and file observations](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.10.0/docs/CHAT-WORK.md).

## Turn assessment into the next useful action

The existing read-only `assess` response now adds `followUp`. It uses the original completion conditions, validated result, current execution record and selected-file inspection to identify the next actions. The original conservative `assessment` remains unchanged.

| Situation | Follow-up behavior |
| --- | --- |
| Invalid record, stale context or unavailable files | Resolve the prerequisite before suggesting reuse or another check |
| A role has not returned, or exceeded its scope | Recover the actual role outcome or inspect the scope violation |
| Implementation, review or verification explicitly failed | Fix the reported failure; another pass does not hide it |
| A relevant check's selected files changed | Rerun the affected unit or conditions |
| Files are stable but evidence has inconsistent IDs, methods, versions or duplicates | Reconcile the report with actual evidence before deciding that a rerun is needed |
| A required check was not run | Run the outstanding check |
| A condition has no execution evidence | Inspect what actually ran; missing evidence alone is not proof of non-execution |
| An original required manual/static condition remains | Perform that condition's direct confirmation |
| Automatic conditions have consistent current evidence and no other issue remains | Return no additional actions and wait for the next request |

Follow-up references the relevant condition IDs, work units or submitted test/problem indexes. Actions are grouped into at most 12 kinds with bounded references. They do not copy arbitrary report text into executable commands. The host reads the whole action list, verifies the actual evidence, performs authorized work and then saves a concise checkpoint with the remaining next action.

`followUp` is a projection of the current assessment context, not a new persisted history. It does not run commands or save itself. It explicitly remains reference-only, does not authorize execution, does not verify host reports, and does not record user acceptance.

For example, when one display file changes after a successful booking check, the host can preserve the still-applicable booking evidence and rerun the affected display check. If an overall artifact identifier is stale, the host first reconciles the linkage rather than claiming every file changed. This behavior depends on the selected observations and actual host evidence; it is not a general dependency analysis of the entire application.

See [assessment follow-up](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.10.0/docs/CHAT-FOLLOWUP.md).

## Preserve honest completion boundaries

Agent-reported success, selected-file consistency, VAS assessment and user acceptance remain distinct. The session CLI does not collect authenticated user acceptance. A task with only automatic conditions can therefore have an assessment of `needs-verification` and an empty follow-up action list at the same time.

That combination does not require the agent to invent a new manual test or ask again for already-authorized work. The final report should explain the actual checks, any remaining actions and the assessment boundary. Originally required manual/static conditions still remain visible; explicit failures and blockers still require attention.

Automatic iteration numbering, a complete result history, automatic migration between installations and autonomous background execution are not added. The latest progress and execution records are bounded local context, not a guarantee that every coding model will follow the workflow correctly.

## Upgrade and continue

1. Download `VAS-2.10.0-windows.zip` from the [2.10.0 release](https://github.com/zmsqnfl-commits/quintpact-vas/releases/tag/v2.10.0). `SHA256SUMS.txt` and `release-manifest.json` identify the artifacts and packaged source.
2. Close the old runtime and back up the installation and user data. To continue the same installation's task lookup, retain the same VAS installation path and preserve its separate PC-private session store. Do not remove application folders or user files while replacing the product.
3. Open a fresh conversation with the VAS folder selected and ask to resume the saved task. The agent reads the current settings, any latest progress and execution context, then checks the actual application before proceeding.
4. Older settings without blocking questions, progress or execution records remain supported. Missing records remain absent; the upgrade does not manufacture historical checks. If a task requires privacy review, the main agent reviews and saves the full settings first.
5. Continue with ordinary requests. The main agent handles preparation, work records, actual tools, assessment and checkpoint readback; users do not need to create result JSON.

Extracting to a different path or moving to another PC does not automatically migrate private sessions or target bindings. Copying only the VAS folder or a public settings export does not reconstruct those bindings. See [saved settings](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.10.0/docs/CHAT-STATE.md) before relocating an active installation.

`VAS-Client-Form-2.10.0.zip` remains the standalone request form. Requirements remain Windows 10 or 11, PowerShell 5.1 or later, and Python 3.10+ available to the coding host for session commands. No Python interpreter or coding AI is bundled. GitHub Pages and standalone HTML do not connect to the PC's saved chat sessions.

The [2.9.2 storage, privacy and recovery policies](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.10.0/docs/releases/2.9.2.md) remain in effect. This release does not introduce a new hard quota for every file in the memory directory.

## Verification and limits

The [2.10.0 agent-flow verification record](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.10.0/docs/verification/2.10.0-agent-flow.md) separates automated regressions, fresh coding-host observations and release-artifact checks. [GitHub Actions](https://github.com/zmsqnfl-commits/quintpact-vas/actions) provides the published workflow results.

Regression scope includes question readiness, revision conflicts, private-state boundaries, checkpoint failures, role return states, scope violations, changed file observations, contradictory evidence and scoped follow-up. Integration scenarios exercise actual test commands across fresh CLI processes. Separate coding-host exercises inspect real implementation, saved-progress resume, review failure and selective reruns; deterministic CLI tests are not presented as model-behavior evidence.

Python, browser, session/design integration and extracted-package checks cover the VAS product. Application-specific validation and user acceptance remain separate. Skipped checks are reported as skipped, and successful scenarios do not establish a reliability rate across all models or hosts.

Raw conversations, private absolute paths, runtime credentials, local session stores and raw tool logs are kept outside the product and release assets. Shared documentation summarizes the observed behavior and its boundaries without treating saved reports or matching hashes as proof of execution.
