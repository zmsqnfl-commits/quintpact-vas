# VAS 2.9.2 — Safer local storage, broader redaction and reliable task upgrades

VAS 2.9.2 improves the local storage and privacy boundaries behind the conversational workflow. It limits memory recovery files, protects runtime credential files, recognizes more encoded credentials, and preserves access to valid older tasks when the current privacy rules require a review. The Design Studio, interactive samples and established screen-based handoff remain available.

The patch builds on [2.9.1](https://github.com/zmsqnfl-commits/quintpact-vas/releases/tag/v2.9.1). Handoff v3 and result v1 remain compatible. VAS prepares settings and compares submitted evidence; implementation, application testing and any agent delegation still use the coding host's actual tools and permissions.

## Older tasks can be reviewed without losing the rest of the workflow

Stronger privacy rules can change text that a previous version accepted. Previously, one such saved task could prevent the session store from being read, including otherwise valid tasks. Version 2.9.2 distinguishes a privacy-only text change from an invalid setting or binding.

A structurally valid older task now opens as a sanitized copy. The response identifies affected fields in `reviewFields`, while the original saved data remains unchanged. Listing, resuming, exporting and preparing a task do not silently migrate or rewrite that data. Other valid tasks remain usable.

For the affected task, `prepare` returns `needs-input` with `settings.review`. The main coding agent reads the sanitized requirements, resolves any missing meaning with the user, and saves the complete settings against the current revision. Only a successful full save advances the revision and clears the review requirement. The connected design screen explains the situation and blocks a design-only save from standing in for the full review.

This is a narrow upgrade path for text affected by the privacy filter. Unknown fields, incorrect types, invalid bindings and malformed stores are still rejected. Reading a sanitized view is not proof that the application was implemented or tested, and the upgrade does not automatically accept an earlier execution result.

See [saved settings](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.9.2/docs/CHAT-STATE.md) and [implementation and verification](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.9.2/docs/CHAT-EXECUTION.md).

## Memory recovery has explicit capacity and preservation rules

The Windows memory store retains its existing cumulative limit of **10,000 events and 8 MiB of serialized UTF-8 data**. This patch adds limits for the related files that previously sat outside that bound:

| Managed data | Capacity and behavior |
| --- | --- |
| Current `memory.json` | 10,000 events and 8 MiB |
| Previous `memory.previous.json` | One file, up to 8 MiB; replaced by the previous valid store during a normal save |
| Corrupt originals, `memory.corrupt-*.json` | Up to 10 files totaling 16 MiB; never automatically deleted |
| Recognized `.memory-*.tmp` and `.consent-*.tmp` files | Up to 32 files totaling 8 MiB; only regular files with the expected GUID name older than 24 hours are eligible for automatic cleanup |

The normal retained total for these managed files is **40 MiB**. A record write can temporarily require **48 MiB** including its new temporary file. Small consent settings, runtime files and unrelated files are excluded. This is a policy for recognized memory files, not a quota on every file in the directory.

Corrupt originals receive distinct names containing a timestamp and random identifier; a later recovery does not overwrite an earlier original. If another original would exceed the history limit, VAS leaves the current file in place and reports that recovery is needed. It does not truncate the file or silently delete older recovery material to make room.

When the current store is readable, exceeding a history limit still allows listing, export and turning recording off. Additional recording, edits, merge imports and pause changes return `413 memory_history_limit_exceeded`. A corrupt current file that cannot be retained for recovery cannot be listed or exported; recording can still be turned off. Preserve any needed files separately before explicitly clearing the store.

Explicit deletion and replacement imports also clean the reserved backup, recovery and temporary files. The replacement current store is committed first, so a failed write leaves the recovery files intact. If only the subsequent cleanup fails, VAS reports that failure instead of presenting the operation as entirely successful. Cleanup can be retried after the file lock or access problem is resolved.

Automatic temporary-file cleanup runs under the memory lock during startup and access. Recent temporary files, names outside the recognized pattern and link targets are not automatically removed. A locked file that cannot be cleaned remains counted without blocking an otherwise valid read or opt-out.

### Consent remains separate from managing your existing data

Creating, editing or importing records still requires explicit server-side consent. Imported consent fields and browser-only preferences cannot enable Windows recording. Turning recording off preserves existing records. Authenticated users can list, export, delete or clear supported-size existing records without turning recording back on; a deletion control is not gated behind permission to record new data.

Pause remains separate from consent, and browser-local memory remains separate from Windows memory. Optional work memory, saved chat settings and form-draft recovery are distinct features. Disabling memory does not delete chat tasks or application files.

## Runtime credential files use restricted Windows permissions

Runtime state files and their temporary files now use a protected access-control list limited to the current Windows user, SYSTEM and administrators. Temporary files receive those permissions before credential data is written. Reusing a runtime file requires checks of its path, owner and permissions. Parent directories and user-selected state directories do not have their permissions rewritten.

Windows memory and runtime state must use actual local folders. Paths containing symbolic links or junctions, and network, UNC, device or alternate-data-stream paths, are rejected. The VAS product source can still live on a NAS; the private runtime state stays local to the PC. An invalid memory path returns `503 memory_path_invalid` without deleting the existing data or retrying with weaker permissions.

The launcher no longer prints the authentication token in `VAS_READY` or its console URL. A `-NoBrowser` launch prepares the server and prints a token-free address; the agent's documented connection procedure supplies authenticated access when needed.

The credential remains a plaintext local authentication value, not an encrypted secret vault. These file permissions do not exclude processes running as the same user or an administrator. The path checks target reparse points and do not claim to eliminate hard-link attacks or all adversarial file-replacement races.

The initial browser connection URL still carries authentication. When browser storage is available, the client removes it from the visible URL; a restricted-storage fallback can carry it in the fragment. Keep those connection URLs private. Removing console output does not turn URL bootstrap into a one-time code exchange.

## More encoded and split credential forms are redacted

The shared Python and JavaScript handoff filters, browser memory, Windows memory and bundled knowledge-index builder now cover additional known credential patterns hidden by encoded punctuation, quoted values or static string joins.

Detection uses at most two decoding passes for supported Unicode and hex escapes, ASCII percent escapes and supported HTML entities, along with Unicode compatibility normalization and removal of zero-width or bidirectional controls. It recognizes supported static literal combinations, including adjacent or joined literals. It does not evaluate expressions or execute supplied code.

Ordinary URLs, JSON, design tokens and other tested non-sensitive text retain their original representation. When a transformed form exposes a known credential pattern, VAS can exclude the entire containing string instead of trying to preserve an ambiguous fragment. The coding agent may therefore need to restate an affected requirement without its secret value.

The knowledge index applies redaction before splitting documents into headings and chunks, so a multiline credential or sensitive heading cannot evade filtering through chunk boundaries. It preserves source references for retained content and excludes a source path that itself matches a sensitive pattern instead of inventing a replacement link.

This is bounded, known-pattern protection. It does not identify every unmarked secret, arbitrary encryption, unlimited encoding depth or value assembled only at runtime. Existing disk originals are not erased merely because a safe view or export is generated. Check the shared output before sending it, and keep real credentials out of requirements and reference material.

## Optional RAG references are quoted records with provenance

The compatibility RAG module now packages selected material as a JSON array of quoted records containing its kind, source, line, timestamp, title and text. It normalizes obscured role and boundary markers in both content and metadata, escapes markup delimiters, and keeps the outer untrusted-data warning intact.

When the prompt budget is tight, the module truncates a record's text and marks it as truncated. It does not cut serialized JSON or the outer boundary in half. Normal reference content and the base prompt are preserved by regression coverage.

This does not add RAG to the default screens or automatically insert work memory into a handoff. The compatibility module remains optional, and selected source text remains untrusted data. A clearer serialization boundary is not a guarantee that an external coding AI will ignore every instruction embedded in that data. The coding host must still follow the current user's request and inspect the actual project.

See the [handoff guide](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.9.2/docs/HANDOFF.md) for the default flow and compatibility boundaries.

## Invalid requests return specific errors

| Request problem | HTTP response |
| --- | --- |
| Unsupported memory import mode | `400 invalid_memory_mode` |
| Invalid JSON in the shared API body reader | `400 invalid_json` |
| Shared API request body larger than 5 MiB | `413 request_body_too_large` |
| Memory recovery/history capacity exceeded | `413 memory_history_limit_exceeded` |
| Unsafe or unsupported memory state path | `503 memory_path_invalid` |

Authentication is checked before request-body handling. The chat API keeps its separate 64 KiB body limit. Public health checks, static requests and failed authentication still do not extend the idle timeout introduced in 2.9.1; authenticated API activity, including a connected tab's heartbeat, does.

## Upgrade and recovery

1. Download `VAS-2.9.2-windows.zip` from the [2.9.2 release](https://github.com/zmsqnfl-commits/quintpact-vas/releases/tag/v2.9.2). `SHA256SUMS.txt` and `release-manifest.json` identify the files and source used for the package.
2. Close the old runtime and keep a backup of the installation and any user data. Extract the complete new package. To continue the same installation's saved tasks, retain the same VAS installation path and preserve its separate private local settings store; do not erase application folders or user files during replacement.
3. Open a fresh conversation with the VAS folder selected and ask to continue the saved task. The main agent handles the lookup, review, full save and preparation commands. You do not need to edit a settings file or author a result JSON.
4. If a task needs privacy review, confirm the meaning of the sanitized requirements in that conversation before continuing. A design-screen save alone cannot complete this review. Unaffected tasks can continue normally.
5. Check whether you want optional work memory enabled. If storage or recovery limits are reached, keep recording off, preserve or export any needed data, and use explicit deletion or replacement only when you intend that cleanup. VAS does not automatically delete corrupt originals.

Extracting VAS at another path or moving to another PC does **not** automatically migrate chat sessions or private target bindings. Copying only the product folder is not a backup of the private settings store, and public setting exports do not reconstruct private bindings. See [saved settings](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.9.2/docs/CHAT-STATE.md) and [operations](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.9.2/docs/OPERATIONS.md) before relocating an active installation.

`VAS-Client-Form-2.9.2.zip` remains the standalone request form. Requirements remain Windows 10 or 11, PowerShell 5.1 or later, and Python 3.10+ available to the coding host for chat-session commands. No Python interpreter or coding AI is bundled. GitHub Pages and standalone HTML do not connect to the PC's saved chat sessions.

## Verification scope

The implementation candidate at commit `59ff9a8` completed **928 Python tests, 173 browser tests, 17 session/design integration checks, 10 package checks, 4 package-boundary checks and an extracted-package runtime check**. Three Windows symbolic-link tests were skipped because the executing environment lacked the required link-creation permission; those skips are not passes.

Coverage includes rejected-write preservation, memory history limits and cleanup failures, invalid API bodies, runtime-file permissions and path rejection, encoded-credential regressions with non-sensitive controls, quoted RAG boundaries, and the saved-task flow through settings, design, preparation, assessment and restart. Older-task tests cover a sanitized read without a disk rewrite, review-gated preparation, blocked design-only saves, revision advancement after a full save, and continued access to unrelated valid tasks.

These are candidate verification results, not a claim that the final release workflow has already passed or that every external coding host behaves identically. The final package manifest identifies its source, and [GitHub Actions](https://github.com/zmsqnfl-commits/quintpact-vas/actions) provides the published workflow results. Application-specific tests, manual checks and user acceptance remain separate from VAS's own checks.

Private execution logs, runtime credentials, local paths and user memory are excluded from the release artifacts. The patch improves the tested storage and data-handling behavior without certifying an AI's execution or guaranteeing that all secrets and instruction-injection attempts are detected.
