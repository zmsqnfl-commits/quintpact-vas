# VAS 2.7.5 — Portable memory and stronger output checks

VAS 2.7.5 repairs three confirmed privacy/control gaps and makes browser and Windows work-memory transfers work together. The default workflow remains: describe the task, confirm a design, copy the prompt, then inspect, implement and verify the real project in the coding host.

## What changed

- **Credential-bearing indexed expressions and XML are withheld.** The shared browser/Python filters cover bracket targets, escaped credential labels, comments around assignments, triple/adjacent strings, XML namespaces, attributes, CDATA, nested markup and unclosed credential elements. Approved source ZIPs reject affected files before adding excerpts. Windows and browser memory filters apply the same protection to stored text.
- **Private property names are filtered as well as values.** Paths, filenames, contact details and recognizable credential strings cannot survive as memory JSON keys. The check covers nested objects, both PowerShell object representations, current writes, imports and historical exports. Unsafe properties are omitted instead of being renamed into colliding keys.
- **Memory exports cross the browser/Windows boundary.** Windows exports include `schema: 1` while retaining their existing `format` and `version`. The browser accepts older Windows format/version envelopes when `schema` is absent; an explicit unsupported schema is rejected.
- **Repeated imports preserve identity.** Windows normalizes UUIDs to its existing 32-hex API IDs and deterministically maps valid legacy browser IDs. Browser merges match these portable identities while retaining the original local ID for deletion. No API route is widened. One-item arrays retain their array shape in Windows memory.
- **Optional commit guards read the staged blobs.** A staged credential cannot pass because an unstaged working copy was cleaned. Literal filenames are handled without shell splitting; Git/read failures block the check. The PowerShell template is encoded for Windows PowerShell 5.1.

The hook templates remain optional. Copy `check-staged.py` beside the chosen hook when installing it. They require Python and Git; `SKIP_SENSITIVE=1` overrides a detected pattern only, not a failed inspection. Their recognized assignment policy remains narrower than the application handoff filter.

## Verification

Release validation covers Python contracts, browser flows, actual Windows APIs, reproducible packages and the extracted Windows application. Additional tests exercise property-name privacy, UUID/legacy-ID roundtrips, repeated merges, native API update/delete, literal staged filenames, partial staging, copied hooks and normal JSON/XML/source controls.

Local Windows validation passed **285 Python checks** and **99 browser scenarios**. The single directory-symlink permission skip was then exercised in an administrator process using an isolated synthetic fixture: **1 passed, 0 skipped**, bringing the verified Python total to **286**. The test and implementation hashes matched before and after that check. Package checks passed **7 tests**; the extracted Windows workflow passed **1 test**; release boundaries passed **4 tests** with packaged source hashes matching the checkout.

The shared suite contains **74 synthetic credential cases**. One independent candidate review exposed additional indexed/XML forms, filename keys and a browser environment without Web Crypto; those cases were reproduced, fixed and added to regression coverage. JavaScript's portable identity mapping was compared with standard SHA-256 across all supported legacy-ID lengths. All 14 offered design directions retained the final long-form requirements and complete design instructions.

GitHub Actions runs the final [CI and release gates](https://github.com/zmsqnfl-commits/quintpact-vas/actions). The generated release manifest identifies the exact commit and artifact hashes. The source assessment was scoped to connected application and development boundaries; it did not exhaustively review every passive asset, historical document or test file in the 287-file baseline inventory.

## Upgrade and limits

Close the previous VAS session and launch the updated `VAS-source` checkout or extracted Windows ZIP. Preserve user data and design selections. Keep the working folder name stable; release artifacts carry the version.

Filtering on historical reads does not rewrite old disk originals or files already shared elsewhere. Existing duplicates created by earlier imports are retained; this patch prevents new duplicate merges. Explicit memory deletion continues to remove application-managed history copies. Source/recovery backups and saved browser drafts are separate data.

Credential XML and ambiguous source expressions may cause the whole input string to be withheld, including harmless surrounding settings. Review the generated prompt and re-enter those settings separately. Unknown, unlabeled secrets are not guaranteed detectable. Legacy-ID matching uses the same bounded SHA-256 mapping in Windows and JavaScript, including browsers without Web Crypto.

This is a source review and synthetic integration verification, not a security certification. External coding-host execution, OS/NAS permissions, remote access policy and previously shared files remain outside the checks. VAS role instructions do not create a sandbox or prove that another host ran tests. The optional ten-repeat stress suite is not part of this recheck.
