# VAS 2.9.1 — Server-enforced memory controls and clearer handoffs

VAS 2.9.1 is a patch release for the conversational workflow introduced in [2.9.0](https://github.com/zmsqnfl-commits/quintpact-vas/releases/tag/v2.9.0). It strengthens Windows work-memory consent and storage limits, corrects idle-time accounting, and aligns existing-application result compatibility. It also makes runtime limitations and the next action in the coding conversation easier to understand.

Handoff v3 and result v1 remain compatible. This release does not introduce an autonomous agent runtime, automatic iteration chaining or automatic conversion between browser handoffs and chat-session execution. VAS organizes settings and compares submitted evidence; actual implementation and testing still use the coding host's tools and permissions.

## Work-memory consent is enforced by the Windows server

Previously, the browser checked consent before recording, but direct authenticated calls to the memory API did not enforce the same choice. Event creation, event updates and imports now require explicit consent at the server boundary. Without consent, those requests return HTTP 403 with `memory_consent_required`.

The server keeps consent in a small, separate `memory-consent.json` file under the local memory store, protected by the same lock used for memory changes. Only a valid explicit boolean opt-in enables recording. A missing or invalid consent setting means recording is off. Consent fields in old event data or an imported file cannot grant permission, and the runtime does not migrate an IndexedDB opt-in into server consent.

This separation matters when storage is full: changing the recording preference does not require rewriting the event file or finding spare capacity in it. Turning recording off and choosing **Start without memory** remain possible at the exact size limit and with oversized legacy data. A failed write is not reported as a successful preference change.

Turning recording off preserves existing records. For stores within the supported limits, users can still list, export, delete or clear their records without turning recording on again. Pause remains a separate control: it stops automatic recording, while a user-requested import remains available when explicit consent is still enabled.

These rules apply to the Windows runtime. Browser-only memory continues to use its own browser-local consent and storage. Optional work memory, saved chat-task settings and form-draft recovery are separate features; disabling memory does not erase saved chat tasks or project files.

## Cumulative limits protect the stored data

Windows work memory is bounded by both:

- **10,000 events** in the final store, after import merging and ID deduplication.
- **8 MiB (8,388,608 bytes)** for the serialized UTF-8 event store, including its metadata.

The server checks the final data before replacement. Adds, edits or imports that exceed either limit return HTTP 413 with `memory_limit_exceeded`, preserving the existing event file. A small individual request cannot bypass the cumulative limit by appending to a nearly full store.

An older file that already exceeds a limit is kept intact and reported as requiring recovery. The server does not quarantine it as corrupt, truncate it or remove records automatically. Normal reading and additional recording are blocked for that oversized store, but opting out and starting without memory remain available. Explicitly clearing the oversized store creates an empty store with recording off. Clearing it is a deletion decision, so preserve any data you need before choosing that action.

See the [operations guide](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.9.1/docs/OPERATIONS.md) for storage locations, recovery behavior and the distinction between pause, opt-out and deletion.

## Open controls reflect the current memory setting

The runtime adapter reads current server consent instead of relying on a stale browser preference. Same-origin tabs notify one another when a memory setting changes. Visible memory controls refresh on that notification and when the screen regains focus or becomes visible again.

The refresh also clears previous action feedback, so an earlier “memory enabled” message does not remain beside a now-disabled state. This synchronization concerns the work-memory controls; it does not execute the coding AI or change a chat task's design revision.

## Idle shutdown counts authenticated activity

Public `/health` checks, static asset requests and requests rejected by authentication or origin checks no longer reset the local server's idle timer. The request loop checks expiry even while requests continue arriving, preventing steady public traffic from keeping an otherwise idle server alive.

Successful authentication for API access counts as activity, including the heartbeat sent by a connected VAS tab. With no authenticated requests, the default shutdown interval is 30 minutes. A connected tab can therefore keep the server available; if the browser suspends background requests, a tab being open does not guarantee that the server remains running. This is a connection-idle policy, not a measurement of keyboard or mouse activity.

## Existing-application reports use a compatible source type

The chat execution CLI now treats a result's legacy `registered` source type as equivalent to `existing`, matching the established result-validation contract. It still requires the current handoff ID, payload hash and iteration to match. A `new` result does not become compatible with an existing application through this alias.

Current settings, revision and role resources still determine the prepared handoff. A stale result cannot become valid by relabeling its source type. Rework continues by preparing against the latest settings; automatic `iteration + 1` history and result chaining are not part of this patch.

## Setup shows the next action and runtime limitations

The new-project and existing-project screens explain how to continue with the coding AI after setup. A connected VAS conversation uses the latest saved task settings; a copied browser prompt follows the established handoff workflow. Users do not need to manually run `prepare` or author a result JSON to continue the conversation. The main coding agent handles preparation and assessment where that workflow is supported.

If the Windows launcher cannot start the local server, it explains the restricted file-based mode:

| Capability | Without the local Windows runtime |
| --- | --- |
| Design comparison and requirement entry | Available |
| Browser-local design and draft storage | Available when the browser permits storage |
| Project-folder path | Can be entered or pasted; the Windows picker is unavailable |
| Prompt copying and handoff JSON export | Available; displayed text can be copied manually if clipboard access is denied |
| Connected chat-task design synchronization | Unavailable |
| Windows work memory and runtime APIs | Unavailable; browser-local memory follows its own consent and storage settings |

Saving a design in browser storage does not save it into a connected chat session. The [handoff guide](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.9.1/docs/HANDOFF.md) and [chat execution guide](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.9.1/docs/CHAT-EXECUTION.md) describe the respective next steps. Legacy result-import and RAG review modules remain available for compatibility rather than being added back to the default screen.

## Upgrade and recovery

1. Download `VAS-2.9.1-windows.zip` and verify it against the published `SHA256SUMS.txt` and `release-manifest.json`.
2. Keep a backup of the previous installation and any user data, then extract the complete archive. Open a fresh coding-host conversation to load the current project instructions.
3. Check the work-memory preference. When no server consent setting exists, Windows recording starts off while existing records remain on disk. Enable it only if you want future confirmed design selections recorded.
4. If an older store exceeds the limits, continue with memory off and retain any needed data before explicitly clearing the store. The upgrade does not silently discard that data.

`VAS-Client-Form-2.9.1.zip` remains the standalone request form. Chat sessions are associated with the VAS installation path: extracting to another path or switching PCs does not automatically migrate old sessions or their private target bindings. See [saved settings](https://github.com/zmsqnfl-commits/quintpact-vas/blob/v2.9.1/docs/CHAT-STATE.md) before moving an installation with active tasks.

No Python interpreter or coding AI is bundled. The local chat workflow continues to require Windows 10 or 11, PowerShell 5.1 or later, Python 3.10+ available to the coding host, and the host's actual file, command and local-store permissions.

## Verification scope

The release gates are:

```powershell
npm.cmd run test:python
npm.cmd run test:browser
npm.cmd run test:package
npm.cmd run agent:security
```

Focused regression coverage exercises direct HTTP calls with consent disabled, invalid or legacy consent data, persisted consent changes, paused recording, cumulative count and byte limits, import merging, unchanged files after rejected writes, full-store opt-out, oversized-store recovery, and authenticated versus public idle traffic. Browser coverage checks ordinary handoff flows, memory controls across tabs, focus refresh and continuing without memory. Result tests check the `registered` alias while retaining ID, hash, iteration and new-versus-existing mismatch rejection.

Both Windows CI and the required Windows release job include the memory-policy regressions. Each Windows test and build command runs as its own workflow step, so a later successful command cannot hide an earlier failure or allow publication after a failed Windows check.

The external-folder symbolic-link check is permission-sensitive on Windows. It verifies that project import skips the link and does not copy the external file; a skipped test is not a pass. The prepared patch was also checked with link-creation permission. Release workflow logs and artifact manifests identify the checks and source for each published package.

These checks establish the tested product behavior, not a guarantee that every coding AI completed every application correctly. Application-specific tests, direct user confirmation and remaining manual checks stay separate. Private execution logs, local paths, runtime credentials and user memory are excluded from the release artifacts.
