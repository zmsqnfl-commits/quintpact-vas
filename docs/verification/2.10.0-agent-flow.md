# VAS 2.10.0 agent workflow validation

This report separates automated regression checks, actual coding-host observations and release-artifact verification. A test result applies to the tested source and scenario; it does not certify every model or host.

## Reproducible checks

The Python suite covers session revision conflicts, private state, question readiness, checkpoints, work records, selected-file changes, failed or unreturned roles, and read-only assessment and follow-up. `tests/test_session_delivery_flow.py` connects these operations across fresh CLI processes and real Python test commands. These are deterministic integration checks, not model-behavior tests.

Browser checks cover the existing request, design, privacy and runtime paths. Package checks inspect the Windows ZIP and standalone form, exercise extracted session commands, and check the Pages boundary. `tests/test_release_runtime_flow.py` starts the extracted Windows runtime in an isolated location.

## Actual coding-host scope

The release validation used an isolated booking application, a separate PC-private session store and two fresh Codex processes. The first conversation added the implementation, preserved all four provided files, and stopped before testing as requested. It saved a paused checkpoint with the unperformed checks and the next verification action. The second conversation resumed the saved work, ran all five provided tests plus additional API checks successfully, and preserved the application's five files. A separate verification run also passed the five tests.

The second conversation recorded the actual checks, assessed the report and saved a new checkpoint with readback. Automatic conditions C1-C3 were reusable. The original required static condition C4, covering the stated library and file-preservation constraints, remained on the direct-confirmation route; assessment stayed `needs-verification`. The saved next action described that remaining boundary without claiming user acceptance or asking again before already-authorized tests.

The first host initially supplied an invalid result shape and recovered after the CLI rejected it; it also recovered from a Windows search-glob error. Neither attempt was silently accepted as success. The second host's 14 observed commands returned successfully. These observations describe this run, not a promise of error-free model behavior.

Earlier staged checks also exercised actual delegated review failures and selective reruns: unchanged booking checks were reused while only the changed display check group ran again. Those observations remain separate from this release's fresh end-to-end run.

## Evidence boundaries

- VAS does not run the application or authenticate a host's reported execution. The coding host performs the commands; its observable tool results are reviewed separately.
- A selected-file sample establishes only the observed bytes. It does not cover omitted inputs, external tools or the entire environment.
- `assessment`, automatic-check reports and user acceptance are separate. An automatic-only task can have no remaining actions while assessment still says `needs-verification`.
- A checkpoint changes the session revision. Older work remains historical context and is not relabeled as a new run.
- CI exercises code and packages; it does not launch a real coding model. Actual-host checks do not establish reliability rates or validate every supported host.
- Raw conversations, paths, private state and tool logs are retained outside the product and release assets.
